Modern UI frameworks bundle reactivity and rendering. You adopt the whole system or none of it. ElementsKit separates the two so you can mix one piece with any framework, or build your own component model from the parts.

## What you get

- **Signals** are the reactive core — fine-grained, framework-agnostic, composable with any rendering model.
- **JSX** compiles to real `document.createElement` calls — no virtual DOM, no diffing, no runtime overhead.
- **Custom elements** are native browser components — ElementsKit enhances them with signals and JSX without wrapping or abstracting the platform.

Use one piece, or all three. Integrate with React for complex UIs. Build web components that work anywhere HTML does.

## How it compares

| Library | Reactivity | Rendering | Standalone core | Custom elements |
|---------|-----------|-----------|:---------------:|:---------------:|
| **ElementsKit** | Fine-grained signals | Real DOM, live bindings | ✓ | First-class |
| React | Re-render tree on `setState` | Virtual DOM + diff | – | Consumer only |
| Solid | Fine-grained signals | Real DOM, live bindings | – | Consumer only |
| Lit | Manual (`@state`) | `lit-html` template diff | ✓ | First-class |
| Preact Signals | Fine-grained signals | Via Preact renderer | Partial | Consumer only |

Closest siblings: **Solid** (same reactivity model, no custom-element first-class) and **Lit** (custom-element first-class, no fine-grained signals). ElementsKit is the intersection — signals *and* native custom elements, neither tied to a proprietary renderer.

## Batteries included, framework-optional

Every primitive ships ready to use. `signal`, `computed`, `@reactive`, `createMediaQuery`, `async`, `promise`, `sync`, `For`, stores, custom elements — all in the same package. No separate query client, no state manager, no router to bolt on before you can start.

- **Drop into what you already have.** A `signal` can drive a React component via `useSignal`. A custom element works as a plain HTML tag inside Vue, Svelte, Astro, or no framework at all — no adapter layer.
- **Or stand alone.** Signals + elements + custom elements is a complete app runtime. There's no missing piece you have to glue in to ship.
- **Same primitives either way.** The code you write in standalone mode is the code you write inside a React app. Switching contexts doesn't mean switching libraries.
- **Pay only for what you import.** Every module is a separate subpath export — `elements-kit/signals`, `elements-kit/utilities/async`, `elements-kit/integrations/react`. Bundlers strip everything you don't reference. "Batteries included" doesn't mean "batteries shipped".

## How the pieces fit

The pieces are independent and composable — not a strict hierarchy. Signals are the shared language that connects everything.

- **Signals** power live DOM bindings in JSX and reactive properties in custom elements. They can also be subscribed to directly from any framework.
- **Elements** are a pattern built on top of signals and JSX. The result is a reactive DOM.
- **Custom elements** are a native browser standard. React, Vue, and plain HTML can all use `<x-counter />` as a regular HTML tag — no adapter, no wrapper.
- **Framework integrations** get both sides: shared signal state via `useSignal` / `useScope`, and any custom element as a native HTML tag.

## Which pattern should I use?

| Pattern | When to use it |
|---------|----------------|
| Plain signals | Pure logic, no UI. Node scripts, workers, utilities that need reactive state. |
| Elements / JSX | Inline reactive UI in scripts. Quick components appended directly to the DOM. |
| Components | Class-based UI with `render()`. Share state across multiple elements via stores. |
| Custom elements | Reusable across frameworks. Native HTML integration, Shadow DOM, framework-agnostic distribution. |

Start with the simplest option that fits — you can always combine patterns.

## Not for

ElementsKit is deliberately narrow. Reach for something else if you need:

- **Server-side rendering or streaming HTML.** No SSR, no hydration, no React Server Components. Rendering happens in the browser.
- **A complete app framework.** No router, no data layer, no file-system conventions — bring or compose your own.
- **A pre-built component library.** This ships primitives, not components. A design system on top has to come from you or a third party.

Narrow doesn't mean incomplete — signals + elements + custom elements cover the full client-side reactive-UI surface. The edges are real, and stating them plainly saves everyone's time.

## Explicit beats heuristic

In the age of AI-assisted code generation, writing code isn't the scarce resource — *maintenance* is. A codebase is read and rewritten long after it's first authored, often by an agent rebuilding context from scratch. Implicit behavior makes every edit a re-derivation: was this variable tracked? did this hook run? is this value live or stale?

ElementsKit is explicit by design. The contract is visible at the call site, not hidden in a compiler pass:

- **`signal(0)` is reactive. A plain `let` is not.** No framework rewrites your variables behind your back.
- **If a value is derived, wrap it in `computed(...)`.** No "was this tracked?" heuristic — the call site says so.
- **Props arrive as `Computed<T>` callables.** A read is a `()`. A subscription is passing the getter along. Both visible at the call site.
- **Cleanup is `onCleanup`, not a hook-position rule.** The dependency is named, not implied by call order.

Writing the code is cheap — an agent will draft most of it. What a library is actually worth is the shape of the code after it's been edited a hundred times. Primitives with explicit contracts survive that. Magic doesn't.

## Primitives first, composable abstractions

Small primitives, one job each, typed interfaces at every boundary. Abstraction is assembled, not inherited — compose upward from `signal` → `sync(fromEvent(...), ...)` → `<For>` and stop at the level your feature needs. Designed for AI agents as much as for humans: each step is verifiable on its own, and there's no framework-specific mental model to learn before writing the first line.

- **No prop matrices.** No single-system components with forty flags where legal combinations aren't obvious until you read the source.
- **No hidden coupling.** Blocks meet at their types; invariants don't leak across layers.
- **Close to the platform.** `promise` wraps a native `Promise`. JSX compiles to `document.createElement`. Custom elements are `HTMLElement` subclasses. You already know the underlying shape.
- **Minimal surface.** `async` has no cache, no query client, no query/mutation split. If you need those, compose them on top — don't inherit them by default.
- **Swap, don't rewrite.** Replace one block (`throttled` → `debounced`) without touching the ones around it.
