Modern UI frameworks bundle reactivity, rendering, and lifecycle. You adopt the whole system or none of it. ElementsKit unbundles it into primitives you import à la carte — signals, utilities, JSX, custom elements — and combine in any framework or none. Every module is a separate subpath, so bundlers ship only what you reference.

## Pillars

- **Signals** are the reactive core — fine-grained, framework-agnostic, composable with any rendering model.
- **Utilities** are reactive browser APIs and common patterns built on signals — `on`, `fromEvent`, `sync`, observers, `media-query`, `storage`, `async`.
- **JSX → elements** compiles to real `document.createElement` calls — no virtual DOM, no diffing, no runtime overhead.
- **Custom elements** are native browser components — ElementsKit enhances them with signals and JSX without wrapping or abstracting the platform.

## Design

Three threads run through every API choice:

### Composability over configuration

Frameworks ship one large system you configure with props, plugins, dependency arrays, and idioms. ElementsKit ships small primitives you import and combine. There's no convention to memorize and no hidden config — the call site is the contract. Want a query layer? Compose `async` + `retry` + storage. Want browser-API hooks? Import the utility you need.

### Close to the platform

Heavy abstraction over native APIs is where beginners get burned — they learn the abstraction, not the platform underneath, and the leak surfaces in production. ElementsKit keeps the layer thin or absent. JSX compiles to `document.createElement`. `promise` *extends* the native `Promise` (still awaitable, still chainable). `async` instances are thenable. Custom elements *are* `HTMLElement`. The source itself is small composable pieces, so what you read in the docs maps directly to what you write, and what you write maps directly to what the browser already knows.

### Readable by non-experts

Frameworks often push you toward clever-but-cryptic patterns to get common things done — `useReducer` with a switch, `useEffect` dependency arrays, derived state via `useMemo`, hook-position rules, suspense-driven fetching. Those are landmines for anyone not steeped in the idiom. ElementsKit is the opposite: `signal(0)` is reactive, plain `let` isn't. Stores are plain classes with `@reactive` field decorators — no proxies rewriting property access behind your back. What the debugger shows is what you wrote.

### Built for the AI age

Writing code is cheap — an agent will draft most of it. *Maintaining* it is the bottleneck. A codebase is read and rewritten long after it's first authored, often by an agent rebuilding context from scratch. Implicit behavior makes every edit a re-derivation: was this variable tracked? did this hook run? is this value live or stale?

ElementsKit is explicit at the call site:

- **`signal(0)` is reactive. A plain `let` is not.** No framework rewrites your variables behind your back.
- **If a value is derived, wrap it in `computed(...)`.** No "was this tracked?" heuristic — the call site says so.
- **Props arrive as `Computed<T>` callables.** A read is a `()`. A subscription is passing the getter along.
- **Cleanup is `onCleanup`, not a hook-position rule.** The dependency is named, not implied by call order.

Primitives with explicit contracts survive a hundred edits — by humans or agents. Magic doesn't.

## Compose, don't install

Most teams bolt several layers on top of a UI framework: a **UI framework** (React, Vue, Solid), a **custom-element** library (Lit), a **server-state** library (TanStack Query, SWR), a **browser-hooks** pack (react-use, vueuse, solid-primitives), and a **state** manager (Zustand, Jotai, MobX). ElementsKit covers the whole layer from its primitives. Most of what you'd install is one or two lines away:

| Layer | Feature | ElementsKit |
|-------|---------|-------------|
| **State** | Shared reactive state | `class Store { @reactive() count = 0 }` |
|  | Derived value | `computed(() => store.count * 2)` |
| **Server state** | Query | `async(() => fetch(url())).start()` |
|  | Mutation | `mutation.run({ id, name })` |
|  | Retry with backoff | `async(retry(fn, 5, n => 2**n * 100)).start()` |
|  | Persist result | `async(fetcher.then(v => store(v))).start()` |
| **Browser hooks** | Online / offline | `online()` |
|  | Viewport size | `windowSize.width()` |
|  | Media query | `createMediaQuery("(prefers-color-scheme: dark)")` |
|  | Debounce | `createInterval(300)` |
| **UI framework** | Mount into DOM | `render(el, () => <App/>)` |
|  | Function component | `function Counter(props) { return <div/> }` |
|  | Class component | `class Counter { render() { return <div/> } }` |
|  | Lifecycle cleanup | `onCleanup(() => …)` |
| **Custom elements** | Reactive HTMLElement | `@attributes class X extends HTMLElement {}` |
|  | Reactive property | `@reactive() count = 0` |
|  | Attribute handler | `static [attr] = { name(this, v) {} }` |
|  | Slot | `children = Slot.new()` |

## Framework integration

Any signal can drive a UI-framework component. The hook is the bridge, not the primitive — the same utility works inside React today, Solid or Vue when those integrations ship:

```tsx
/** @jsxImportSource react */
import { online } from "elements-kit/utilities/network";
import { useSignal } from "elements-kit/integrations/react";

export function OfflineBanner() {
  const connected = useSignal(online);
  return connected ? null : <div>You're offline</div>;
}
```

The pieces are independent and composable — not a strict hierarchy. Signals are the shared language that connects everything.

## Pattern guide

| Pattern | When to use it |
|---------|----------------|
| Plain signals | Pure logic, no UI. Node scripts, workers, utilities that need reactive state. |
| Elements / JSX | Inline reactive UI in scripts. Quick components appended directly to the DOM. |
| Components | Class-based UI with `render()`. Share state across multiple elements via stores. |
| Custom elements | Reusable across frameworks. Native HTML integration, Shadow DOM, framework-agnostic distribution. |

Start with the simplest option that fits — you can always combine patterns.

## Not for

ElementsKit is deliberately narrow. Reach for something else if you need:

- **Server-side rendering or streaming HTML.** No SSR, no hydration, no React Server Components. Rendering happens in the browser.
- **A complete app framework.** No router, no data layer, no file-system conventions — bring or compose your own.
- **A pre-built component library.** This ships primitives, not components. A design system on top has to come from you or a third party.

Narrow doesn't mean incomplete — signals + elements + custom elements cover the full client-side reactive-UI surface.
